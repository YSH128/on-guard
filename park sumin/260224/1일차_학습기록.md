## 1. 프로젝트 기획 회의
AI를 활용해 만든 디지털 위조 영상 탐지 기술을 중심으로 어떻게 서비스를 제공할 것인가를 논의했습니다.

팀원들과의 회의를 거쳐, `영상 통화 상황에서 발생할 수 있는 지인 사칭 탐지`를 메인 서비스로 결정했습니다.

대략적인 MVP는 다음과 같습니다. 

### MVP

| index | 기능 | 비고 |
| --- | --- | --- |
| 1 | 영상통화 중 실시간으로 AI 판별 |  |
| 2 | 영상통화 중인지 구분 |  |
| 3 | AI라면 팝업창&알림 |  |
| 4 | AI일때, 레포트 생성 | 어떤 레포트를 작성할것인가(AI 판별 사유 (시각화), 대화 내용, 대화 상대(전화번호, 이름))  |
| 5 | 보호자를 등록해서 보호자에게도 래포트 전달 |   |
| 6 | 대화 내용을 기반으로 위험도(정보유출, 유인, 납치 등) 태그 |  |
| 7 | 태그 별로 분류 |  |


## 2. 구현 계획
해당 서비스는 앱이나 웹의 백그라운드에서 실행될 수 있도록 구성할 것이기 때문에, 어떻게 구현할 수 있을지에 대해 자료 조사를 진행했습니다. 

크게 3가지의 방법을 제시했습니다.

1. 백그라운드에서 항시 실행
2. 영상이 감지될때만 실행
3. 플로팅 아이콘 등을 활용한 수동 실행 

위의 3가지 방법의 장점과 단점, 하드웨어적 한계를 조사했습니다. 

1. **완전 상시 백그라운드 실행**

```cpp
앱/서비스 프로세스가 계속 살아 있고, 항상 화면/스트림을 모니터링하려는 구조
```

- 장점
    - 자동성 최강
        - 유저가 따로 켜지 않아도 항상 감시 → “잊어버려도 보호받는” 느낌.
    - 즉시성
        - 위협 탐지까지 딜레이 최소화 (이론상 가장 빠른 대응).
    - UX 단순
        - “앱 설치만 하면 계속 지켜봐준다”는 메시지 전달이 쉽다.
- 단점
    - 배터리·발열·자원
        - 영상/화면을 상시 스캔하면 CPU/GPU·전력 소모가 커지고, 특히 폰에서 체감 이슈 크다.
    - 프라이버시 불편감
        - “항상 화면/영상이 분석된다”는 심리가 거부감을 부른다 (감시 느낌).
        - 카메라·화면 캡처를 상시 훑는 구조는 개인정보 이슈
    - 오탐·알림 피로
        - 모든 영상/화면에 대해 탐지 → 위험과 무관한 콘텐츠에서도 경고가 뜨면 금방 꺼버리게 된다.
- 구현의 한계
    - OS 정책
        - iOS/안드로이드 모두 백그라운드에서 카메라·스크린을 마음대로 감시하는 걸 허용하지 않음.
        - 백그라운드에서 임의 화면 캡처/분석은 거의 불가능에 가깝고, PC도 보안 솔루션급 권한이 필요.
    - 스토어 심사
        - “항상 다른 앱 화면을 읽는다”는 구조는 앱스토어/플레이스토어 심사에서 튕길 가능성 매우 높음.
    
    → 리서치/실험·엔터프라이즈 보안 솔루션 정도는 가능하지만, 일반 사용자 대상 상용 서비스로는 현실성이 낮은 편.
    

```cpp
OS별 정책
- iOS
	- 백그라운드에서 화면을 계속 캡처 → 불가능
	- 다른 앱 화면을 감시 → 원칙적으로 차단
	- Screen Recording 권한은 있지만:
		- 사용자가 명시적으로 시작해야 함
		- 상단에 빨간 녹화 표시가 뜸
		- 백그라운드 상시 감시는 불가

- 안드로이드 
	- MediaProjection API → 화면 캡처 가능하지만 사용자 동의 필요
	- 백그라운드 무제한 감시는 정책 위반 가능성 높음
	- Android 10+ 이후로 제약 강화
	- Google Play 정책상: 사용자 화면을 분석하는 앱 → 승인 거의 안 남
```

**2. “동영상이 감지될 때만 실행” (자동 트리거 기반)**

```cpp
백그라운드에서 대기하다가, “지금 영상이 재생 중”이라는 시그널을 감지하면 그때만 딥페이크 분석을 켠다.
```

- 장점
    - 자원 절충
        - 평소엔 가벼운 감지 로직만 돌리고, 영상 재생 시에만 무거운 모델 실행 → 상시 대비 자원 부담 감소.
    - 사용자 경험
        - “영상 볼 때만 알아서 켜진다”는 자동성 유지, 사용자가 매번 버튼 안 눌러도 됨.
    - 보안 효과
        - 영상 위주 보호(딥페이크 타깃)에 집중할 수 있어서, 컨셉과도 잘 맞는다.
- 단점
    - 탐지 그레인
        - “무슨 영상인지”까지 알 수 있는 건 아니고, 그냥 재생 여부만 알면 노이즈가 많다.
        - 게임, 넷플릭스, 광고 등까지 다 걸리면 여전히 오탐/알림 피로 문제.
    - 사용자 통제감 부족
        - 유저 입장에서 “언제 켜지는지 정확히 모른다”고 느끼면 여전히 프라이버시 불안.
- 구현 한계
    - “영상 재생 감지” 자체가 쉽지 않음
        - 모바일: OS가 “지금 영상 재생 중”을 범용 API로 안 던져줌. 각 앱(유튜브, 인스타, 카톡 등)마다 내장 플레이어 따로라, 공통 훅이 거의 없다.
        - PC: 일부 미디어 세션 API, 브라우저 확장 등으로 “탭 오디오·비디오 재생 상태”는 잡을 수 있지만, 모든 상황을 커버하긴 어려움.
    - 앱별 특화 필요
        - 결국 “카톡에서 공유된 영상만, 브라우저 유튜브만”처럼 앱/플랫폼별 커스텀 구현이 필요해진다.

→ 범용 OS 수준에서 구현 가능한 건 제한적이라, 실제로는 **특정 앱/플랫폼에 맞춘 부분 자동화** 정도로 수렴할 가능성이 큼.

- **3. 선택적 실행(사용자 트리거 + 일부 자동 보조)**
    
    ```cpp
    서비스는 백그라운드/포그라운드 서비스로 “대기”만 하고,
    
    1. 사용자가 “이 영상 검사하기”를 누르거나
    2. 특정 앱/상황에서만 가벼운 자동 감지를 돌려, 필요할 때 정밀 분석을 켜는 구조
    ```
    
    - 장점
        - 프라이버시·신뢰
            - “네가 선택한 순간에만, 그 영상만 본다”라고 명확히 말할 수 있음 → 감시 느낌 감소.
        - 리소스 효율
            - 무거운 모델은 사용자가 요청할 때만 돌려, 배터리·발열 문제 최소화.
        - 스토어·OS 친화
            - 공유 시트, 인텐트, 브라우저 확장, 데스크톱 오버레이 등 “사용자 액션 후 분석”은 현재 정책에 잘 맞음.
        - UX 설계 자유도
            - 카톡/메신저에서 “의심되면 이 버튼 눌러봐” 같은 온보딩을 넣어 교육 효과도 같이 줄 수 있다.
    - 단점
        - 자동이 아님
            - 사용자가 “의심”을 느껴야만 버튼을 누르기 때문에, “그냥 속아 넘어가는 케이스”는 못 잡는다.
        - 마찰 비용
            - 매번 공유/버튼 누르기 귀찮다고 느끼면 사용률 떨어질 수 있음. 그래서 UI/진입 동선 설계가 매우 중요.
    - 구현 관점
        - 모바일
            - “공유하기 → 딥페이크 검사 앱”
            - 특정 메신저/앱에서는 플로팅 버튼, 알림 액션, 포그라운드 서비스 아이콘 등으로 빠른 진입 지원.
        - PC
            - 브라우저 확장: 현재 탭의 영상 캔버스를 캡처해서 분석, 결과를 오버레이.
            - 데스크톱 앱: 특정 창을 선택(Zoom/Teams/카카오톡) → 그 창만 캡처/분석.
    
    → 현실적으로 가장 구현 가능하고, 스토어/프라이버시/배터리까지 고려는 가능한 방식

### 2-1. 결론
서비스 방향과 OS의 특성을 고려해 다음과 같이 개발 방향을 정했습니다. 

우선 사용자가 명시적으로 권한을 허용하면, 현재 화면에 떠 있는 앱의 패키지명(예: 카카오톡, 인스타그램)이나 화면상의 텍스트, 윈도우 상태 변화를 감지할 수 있습니다. 이를 통해 "카카오톡 앱이 실행 중이고 화면에 '영상통화'라는 텍스트나 특정 UI 요소가 나타났다"는 것을 알아낼 수 있습니다. 

이를 바탕으로 영상통화를 감지하고 AI 모델을 사용해 영상 통화의 AI 사용 여부를 판단하기로 했습니다. 

## 3. AI 특강 수강 
컴퓨터 비전, LLM에 대한 AI 특강을 수강했습니다. 

어탠션, 트랜스포머와 같은 LLM의 기본적인 구조를 복습하는 시간을 가졌습니다. 

LLM의 작동 방식 및 원리는 다음 순서와 같습니다. 
```bash
input -> tokenize -> token embedding -> encoding -> LLM -> output(Logits) -> sampling & decoding
```

또한 GPT, Claude와 같은 생성형 모델들의 특징을 이해하면서 각 모델들이 어느 부분에 장점이 있는지도 알게 되었습니다. 

## 3-1. AI 활용 시 주요 한계와 위험 요소

- 윤리적 문제
- 편향
- 할루시네이션
- 최신 정보 반영 한계
- 복잡한 추론, 상식 부족
- 창의성 한계

프로젝트를 진행하면서 기획, 개발, 발표까지 모두 AI를 적극적으로 활용하고 있는데, 항상 사용할 때 다음과 같은 한계를 인지하고 사용해야 함을 항상 잊지 않도록 노력해야 함을 다시 다짐하는 계기가 되었습니다.
