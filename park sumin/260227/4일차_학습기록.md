# 0227 학습 기록

## 1. VLVM, AI 특강

### 1-1. 주요 내용 정리

* VLVM(Vision-Language Vision Model)의 개념과 구조에 대해 학습했습니다. 이미지 인코더와 텍스트 인코더가 각각 특징을 추출한 뒤, 공통 임베딩 공간에서 정렬되는 방식에 대해 이해했습니다.
* 멀티모달 학습에서의 데이터 정합성 문제와 대규모 사전학습(pretraining)의 중요성을 정리했습니다.
* 실제 응용 사례(이미지 캡셔닝, VQA, 멀티모달 검색)를 통해 이론이 서비스로 연결되는 과정을 확인했습니다.
* 최근 트렌드로 LLM 기반 멀티모달 확장과 instruction tuning 기법의 중요성을 배웠습니다.

## 2. KD 기법, AI 특강

* KD(Knowledge Distillation)의 기본 개념인 teacher-student 구조를 복습했습니다.
* soft label과 temperature scaling이 모델 성능에 미치는 영향을 이해했습니다.
* KD가 모델 경량화뿐 아니라 성능 유지 및 일반화 향상에도 활용된다는 점을 학습했습니다.
* 실제 적용 시 loss 구성(CE + KD loss)과 가중치 조절의 중요성을 정리했습니다.

오늘 학습을 통해 멀티모달 모델 구조에 대한 이해와 모델 경량화 전략을 함께 정리할 수 있었습니다.

## 3. vLLM 스켈레톤 코드 실습 및 환경 구축
### 3-1. 실습 환경 및 도구 활용

WSL(Windows Subsystem for Linux) 환경(Ubuntu 22.04)으로 전환하여 실습을 진행했습니다. vLLM, Ray 등 고성능 연산 라이브러리가 윈도우를 공식 지원하지 않아 리눅스 기반 환경을 구성했습니다.

uv 패키지 매니저를 도입하여 uv sync를 통해 torch, vllm, transformers 등 200개 이상의 AI 관련 패키지를 효율적으로 설치하고 가상환경(.venv)을 관리했습니다.

VS Code의 Remote-WSL 확장을 활용해 Jupyter Notebook을 연동하고, 리눅스 커널 기반의 vllm.ipynb 실습 환경을 구축했습니다.

###3-2. 주요 트러블슈팅 (Troubleshooting)

uv 명령어가 인식되지 않는 문제를 환경 변수(PATH) 적용 이슈로 파악하고, source $HOME/.local/bin/env 실행 및 .bashrc 수정을 통해 해결했습니다.

vLLM 실행 중 EngineDeadError가 발생했습니다.

GPU 메모리 부족 문제는 gpu_memory_utilization 값을 0.75에서 0.4로 낮춰 VRAM 점유율을 최적화하여 해결했습니다.

최신 V1 엔진의 WSL 환경 충돌 문제는 os.environ["VLLM_USE_V1"] = "0" 설정을 통해 안정적인 V0 엔진으로 고정하여 해결했습니다.

Triton 연산 과정에서 C 컴파일러가 없어 RuntimeError가 발생했으며, sudo apt install build-essential 설치로 gcc를 포함한 필수 빌드 도구를 구성해 해결했습니다.

_find_upwards 함수가 skeleton02의 LoRA 어댑터를 찾지 못하는 문제를 폴더명을 upstage-skeleton02-master로 변경하거나 코드 경로를 수정하여 해결했습니다.

윈도우 경로(/mnt/c/...)보다 리눅스 네이티브 경로(~/...)에서 작업하는 것이 성능과 안정성 측면에서 유리함을 확인했습니다.

### 3-3. 핵심 실습 내용

PagedAttention의 개념을 학습했습니다. 가상 메모리 관리 기법을 LLM 추론에 적용하여 KV Cache 사용 효율을 극대화하는 원리를 이해했습니다.

LoRA 어댑터 통합 실습을 진행했습니다. 훈련된 LoRA 가중치를 추론 시점에 동적으로 로드하는 Runtime LoRA 방식과, 사전에 가중치를 병합하는 Merged Model 방식의 차이를 비교하고 각각의 장단점을 정리했습니다.

## 4. 딥페이크 탐지 서비스 백엔드 모니터링 설계 준비
### 4-1. 역할 정리 및 아키텍처 방향 설정

실시간 딥페이크 탐지 서비스에서 백엔드 역할을 재정의했습니다.
초기에는 실시간 제어(차단/알림)까지 담당하는 구조였으나, 현재는 AI 모니터링 전담 역할로 정리되었습니다.

이에 따라 다음과 같은 구조를 확정했습니다:

- AI 모델은 온디바이스(모바일)에서 실행
- 서버는 모델 실행 결과 데이터만 수집
- Redis는 실시간 기능(문자 생성 등)용으로 사용
- MySQL은 AI 모니터링 데이터 저장용으로 사용
- Kubernetes는 MVP 단계에서는 도입하지 않음 (EC2 + Docker 기반 운영)

이를 통해 서비스 구조를 실시간 처리 영역과 모니터링 영역으로 명확히 분리했습니다.

### 4-2. AI Telemetry 설계 방향 정리

AI팀이 제공할 모델 출력 값을 기반으로, 서버에서 수집해야 할 항목을 정의하는 작업을 진행했습니다.

수집 대상 예시
- 모델 버전
- 추론 성공 여부
- 추론 소요 시간 (latency)
- 위험 점수 (risk score)
- 타임스탬프
- 기기 식별 해시값

영상·음성 원본은 저장하지 않고, 결과 데이터만 저장하는 방향으로 설계했습니다.
이를 통해 개인정보 최소 수집 원칙을 유지하면서도 모델 성능 분석이 가능하도록 구조를 정리했습니다.

### 4-3. Telemetry API 및 DB 설계 구조 수립

AI 모델 결과를 서버에 전달하기 위한 Telemetry API 설계 필요성을 정리했습니다.

이 과정에서 다음 사항을 검토했습니다:

- 모바일 ↔ 서버 간 인터페이스 계약 정의의 중요성
- batch 전송 필요 여부
- 트래픽 규모에 따른 DB 부담 분석
- MySQL Docker 환경에서의 데이터 저장 전략

또한, 단건 insert 대신 **batch insert 적용이 필요한 상황과 그 기준(초당 이벤트 수)**에 대해 정리했습니다.

이를 통해 단순 로그 저장이 아닌, 확장성을 고려한 저장 전략을 수립했습니다.

### 4-4. 모니터링 지표 정의 및 시각화 계획

AI 모니터링 시스템의 목적을 다음과 같이 명확히 했습니다:

- 모델 성공률 분석
- 평균 및 상위 지연시간 (p95, p99) 분석
- 모델 버전별 성능 비교
- 이상 징후 탐지

이를 위해 Grafana 기반 대시보드 구성 계획을 수립했습니다.
단순 저장이 아닌, 운영 의사결정에 활용 가능한 지표 체계 구축을 목표로 설정했습니다.

### 4-5. 인프라 범위 및 역할 분리 정리

EC2 단일 서버 환경에서 다음과 같이 방향을 확정했습니다:

- Docker 기반 MySQL 추가
- Redis는 기존 기능 유지
- Kubernetes는 MVP 단계에서 도입하지 않음

이를 통해 현재 단계에서는 인프라 확장보다
AI 모니터링 구조의 정확한 설계와 지표 정의에 집중하는 것이 우선임을 정리했습니다.
