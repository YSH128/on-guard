## 1. 기획 회의

딥페이크 탐지 서비스의 AI 모델 모니터링 기능과 관련된 기획 회의를 진행했습니다.

서비스 구조와 각 팀의 역할을 다시 정리하고, 서버가 수행해야 하는 역할을 명확히 했습니다.

AI 모델은 모바일 디바이스에서 On-device 방식으로 실행되며, 서버는 AI 추론을 수행하지 않고 Telemetry 데이터를 수집하고 저장하는 역할만 담당하기로 했습니다. 모바일 디바이스에서 AI 추론이 발생하면 Telemetry 이벤트가 생성되고, 해당 데이터를 API를 통해 서버로 전송하는 구조로 설계했습니다.

Telemetry 데이터에는 모델 종류, 모델 버전, 추론 성공 여부, 추론 latency, risk score, 디바이스 온도, 세션 정보 등이 포함되며, 서버에서는 이를 MySQL에 저장하여 운영 모니터링과 성능 분석에 활용하기로 했습니다.

또한 향후 Grafana를 활용하여 모델 운영 상태를 시각화하고, 모델 버전별 성능 비교 및 이상 징후 탐지를 수행할 수 있도록 모니터링 시스템을 확장하기로 논의했습니다.

## 2. Spring MVC와 Spring WebFlux 차이 학습

Spring 기반 서버 개발에서 사용하는 두 가지 웹 프레임워크인 Spring MVC와 Spring WebFlux의 차이에 대해 학습했습니다.

Spring MVC는 전통적인 동기 방식의 웹 프레임워크로, 요청이 들어오면 요청마다 하나의 스레드가 할당되어 처리되는 구조입니다. 일반적으로 JPA나 JDBC와 같은 블로킹 기반 데이터 접근 방식을 사용하며, 구조가 단순하고 이해하기 쉬워 대부분의 웹 서비스에서 널리 사용됩니다.

반면 Spring WebFlux는 비동기 논블로킹 방식의 웹 프레임워크로, 이벤트 루프 기반으로 동작하며 적은 스레드로도 많은 요청을 처리할 수 있는 특징이 있습니다. WebFlux에서는 Mono와 Flux 같은 Reactive 타입을 사용하여 데이터를 처리하며, 데이터베이스 접근 또한 R2DBC와 같은 논블로킹 드라이버를 사용하는 경우가 많습니다.

이번 프로젝트에서는 AI 모델 추론이 서버에서 이루어지는 것이 아니라 모바일 디바이스에서 수행되고, 서버의 역할이 Telemetry 데이터 수집 및 저장과 같은 비교적 단순한 API 처리이기 때문에 Spring MVC 기반 구조가 더 적합할 수 있다는 점을 이해했습니다.

또한 현재 프로젝트에서 JPA를 사용하고 있기 때문에 블로킹 기반 데이터 접근 방식과의 호환성을 고려했을 때 Spring MVC가 구현과 유지보수 측면에서 더 안정적인 선택이라는 점도 학습했습니다.

## 3. AI 모델 모니터링 지표 설계 학습

On-device AI 모델의 운영 상태를 모니터링하기 위해 어떤 지표를 수집하고 분석해야 하는지에 대해 학습했습니다.

AI 모델 Telemetry 데이터를 기반으로 다음과 같은 주요 모니터링 지표를 정의했습니다.

- Inference Count: 일정 시간 동안 발생한 AI 추론 요청 수
- Success Rate: 전체 추론 중 성공적으로 수행된 비율
- Failure Rate: 추론 실패 비율
- Average Latency: 평균 추론 수행 시간
- p95 Latency: 전체 요청 중 95%가 처리되는 latency 기준
- p99 Latency: 극단적인 지연 상황을 파악하기 위한 latency 기준
- Model Version Success Rate: 모델 버전별 성공률 비교
- Device Temperature: AI 추론 시 디바이스 온도 상태

특히 AI 서비스에서는 평균 latency보다 p95, p99와 같은 tail latency 지표가 실제 사용자 경험을 판단하는 데 중요한 지표라는 점을 이해했습니다.

또한 현재 AI 모델이 온디바이스 환경에 포팅되는 단계이기 때문에 정확한 성능 기준을 아직 알 수 없으며, 초기 단계에서는 Telemetry 데이터를 수집하여 실제 운영 데이터 기반으로 기준을 설정해야 한다는 점도 학습했습니다.
