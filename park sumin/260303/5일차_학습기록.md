# 0303 학습 기록

## 1. AI Telemetry 데이터 스키마 확정

On-device AI(FACE / DEEPVOICE) 추론 결과를 서버로 전송하기 위한 Telemetry 스키마를 확정했습니다.

### 공통 필드 정의

- model_type (FACE / DEEPVOICE)
- model_version
- inference_success
- failure_type (nullable)
- inference_latency_ms
- risk_score (nullable)
- timestamp (device 기준 시간)
- device_hash
- session_id
- device_temperature

### 설계 결정 사항

- 추론 성공(inference_success)과 판별 결과(risk_score)는 별개의 지표로 관리하기로 결정했습니다.
- bbox 좌표는 운영 필수 지표가 아니므로 제외했습니다.
- 원본 영상/음성 데이터는 서버에 저장하지 않기로 설계했습니다.
- 서버는 추론 판단이 아닌 Telemetry 수집 및 모니터링 역할만 수행하도록 정의했습니다.

## 2. telemetry_log 테이블 구조 초안 설계

MySQL 단일 테이블 구조로 설계했습니다.

### 설계 원칙

- Write-heavy 로그 구조로 설계했습니다.
- FACE / DEEPVOICE는 model_type 컬럼으로 구분하는 단일 테이블 구조를 채택했습니다.
- 인덱스를 최소화하여 쓰기 성능을 고려했습니다.
- device timestamp와 server timestamp를 분리했습니다.

### 주요 컬럼

- id (BIGINT, PK)
- model_type
- model_version
- inference_success
- failure_type
- inference_latency_ms
- risk_score
- device_temperature
- device_hash
- session_id
- event_timestamp (device 기준)
- created_at (server 수신 시간)

### 인덱스 전략

- idx_model_version
- idx_event_timestamp
- idx_device_hash

## 3. Telemetry REST API 구조 설계 방향 수립

아키텍처 기준으로 Telemetry 전용 REST API를 설계하기로 결정했습니다.

### Endpoint

POST /api/v1/telemetry

### 특징

- Batch 전송을 지원하도록 설계했습니다.
- 서버는 판단하지 않고 저장만 수행하도록 정의했습니다.
- JPA Batch Insert 기반으로 구현할 예정입니다.

## 5. 일정 관리 및 작업 순서 재정리

노션 및 지라 작업을 정리하고, 수행 순서를 재구성했습니다.

### Epic 구조 정리

- Telemetry 수집 및 저장 체계 구축
- 모델 성능 지표 집계 및 시각화 구축

### 기획 / BE 역할 구분

- 기획: 스키마 정의, API 설계, 지표 정의, 이상 탐지 기준 수립
- BE: JPA 설정, API 구현, Batch 최적화, 집계 로직 구현, Grafana 구성

### 전체 작업 순서 재정립

1. Telemetry 스키마 확정
2. DB 테이블 설계
3. JPA 설정
4. POST /telemetry 구현
5. Batch Insert 최적화
6. 지표 정의
7. 집계 SQL 작성
8. Grafana 대시보드 구성
9. 알람 설정

작업을 설계 → 저장 → 수집 → 집계 → 시각화 → 알람 순으로 정리했습니다.
